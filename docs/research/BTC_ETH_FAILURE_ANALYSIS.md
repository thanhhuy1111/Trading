# BTC/ETH Failure Analysis

_Generated by `packages/research/failure_analysis.py` from the real, already-executed campaign
artifacts — no numbers here are re-derived by hand or estimated. Source data: `docs/research/
experiments/CANDIDATES.csv` (8,198 real TradeCandidate lineage rows), `EXPERIMENT_LEDGER.csv`,
`GATE_RESULTS.csv`. Full per-(symbol, config) output: `docs/research/experiments/
FAILURE_ANALYSIS.csv`._

## 1. Scope

All 120 experiments from the Full Alpha Research Campaign (`docs/research/
ALPHA_RESEARCH_CAMPAIGN_EVIDENCE.md`): 15 strategy configurations × {BTC/USDT, ETH/USDT} ×
3 out-of-sample walk-forward test folds, 1D candles, 2019-01 to 2026-07. This analysis covers
the **1,090 real closed out-of-sample trades** (candidates with `run_type=OOS_FOLD`,
`status=CLOSED`) produced by those experiments, plus the 30 approved-but-unfilled/still-open
candidates and 1,327 risk-governor-rejected candidates recorded across the full campaign
(all run types) for context.

## 2. Methodology and thresholds

Thresholds are declared here, before any result is discussed, and are identical for both
symbols (`packages/research/failure_analysis.py`):

| Reason code | Trigger condition |
|---|---|
| `LOW_TRADE_COUNT` | total OOS trades < 20 |
| `NEGATIVE_EXPECTANCY` | mean net_return_bps per trade ≤ 0 |
| `NEGATIVE_SHARPE` | mean OOS Sharpe (from `GATE_RESULTS.csv`) < 0 |
| `LOW_PROFIT_FACTOR` | profit factor < 1.0 (net losing overall) |
| `FEES_DOMINATE_EDGE` | gross return > 0 but net return ≤ 0 (costs flipped a gross edge into a net loss) |
| `HIGH_STOP_LOSS_RATE` | ≥ 90% of exits are stop-type (INITIAL_STOP or TRAILING_STOP) |
| `TIMEOUT_DOMINANCE` | **not applicable** — see §4 |
| `REGIME_DEPENDENCE` | ≥ 85% of trades occur in a single `MarketRegime` |
| `SINGLE_FOLD_CONCENTRATION` | ≤ 1 of 3 folds net-positive while the 3-fold aggregate is still net-positive |
| `AGENT_SPECIFIC_LOSS` | an agent with ≥ 5 attributed trades has a negative net_return_bps sum |
| `INSUFFICIENT_GENERALIZATION` | fallback tag when the gate failed but none of the above fired |

| | BTC/USDT | ETH/USDT |

Every single BTC config clears positive expectancy; every single ETH config is net negative.
This is not one bad fold or one bad config — it is uniform across all 15 independently-designed
variants, which is itself informative (see §6).

## 4. Structural findings that apply to *both* symbols (not differentiators)

- **100% of the 1,090 OOS closed trades exited via `TRAILING_STOP`.** Zero exited via
  `INITIAL_STOP` or `TAKE_PROFIT`. This is a property of `ExitProtector`'s trailing-stop logic
  activating before the hard stop or take-profit target is ever reached, on both symbols,
  across every config tested — a system-wide characteristic of the current exit design, not a
  BTC-vs-ETH difference. Because of this, `HIGH_STOP_LOSS_RATE` fires on almost every row
  (15/15 BTC, 15/15 ETH) and is **not** a useful differentiator here, only a flag that the
  take-profit target is effectively unreachable under this exit design — worth revisiting in a
  later checkpoint, out of scope for this one.
- **`TIMEOUT_DOMINANCE` is marked not applicable everywhere.** The current exit model
  (`packages/positions/exit_protector.py`, `ExitTriggerType`) has no time-based exit at all —
  only `INITIAL_STOP`, `TAKE_PROFIT`, `TRAILING_STOP`, `MANUAL`. There is no timeout mechanism
  to measure, so this analysis reports it honestly as not applicable rather than fabricating a
  rate for a mechanism that doesn't exist in the code.
- **Both symbols are heavily `TREND_UP`-regime concentrated**: BTC trades occur in `TREND_UP`
  77–97% of the time depending on config (2 of 15 configs cross the 85% flag threshold); ETH is
  90–97% (15 of 15 flagged). Real crypto history over 2019–2026 is trend-dominated on both
  assets, so this reflects the market data more than a strategy defect — but it does mean the
  campaign has very little OOS evidence for either asset's behavior in `SIDEWAYS` or
  `HIGH_VOLATILITY` regimes (117 and 5 closed trades respectively, system-wide).

## 5. What actually differentiates BTC (pass) from ETH (fail)

**Agent-level attribution is the clearest signal.** `AGENT_SPECIFIC_LOSS` fires on 14/15 configs
for *both* symbols, but the losing agent is different:

- **BTC/USDT**: the negative-contributing agent is consistently `reversion_agent_v1`
  (mean reversion). `trend_agent_v1` generates the large majority of BTC's trades (417 of 518
  BTC OOS closed trades attributed to `trend_agent_v1` — the campaign-wide breakdown) and is
  strongly net positive, which is why BTC clears the gate despite the reversion agent dragging
  on the total. `reversion_loose_bands` and `aggressive_regime` are the only two BTC configs
  with **no** negative agent at all — both configs deliberately let the reversion agent
  participate less (fewer, more selective reversion signals) or widen the regime classifier,
  and `reversion_loose_bands` is the single best-performing BTC config in the whole campaign
  (profit factor 2.27, mean OOS Sharpe 0.999).
- **ETH/USDT**: the negative-contributing agent is `trend_agent_v1` itself, in 14 of 15 configs
  (the one exception, `aggressive_regime`, still ends net-negative overall — see below).
  `trend_agent_v1` generates 509 of 572 (89%) of ETH's OOS closed trades — an even larger share
  than on BTC (80%) — so ETH's result is dominated by the same agent that is BTC's edge source.
  The
  same trend-following logic that is BTC's primary source of edge is ETH's primary source of
  loss. This is the single most important finding of this analysis: **the strategy grid does
  not encode a generic "crypto trend-following edge" — it encodes a BTC-specific one that does
  not transfer to ETH under identical rules, thresholds, and cost assumptions.**
- `aggressive_regime` on ETH has no single flagged negative agent (losses are spread thin
  across a broader/looser regime classification that admits more trades, 47 vs. the ~38 typical
  ETH count) but is still net negative overall (-9.5 bps expectancy, Sharpe -0.03) — the
  broadened regime filter dilutes the loss without reversing its direction.

**Fees are not the story.** Only one row (`ETH/USDT aggressive_regime`) is flagged
`FEES_DOMINATE_EDGE`; every other ETH failure is negative even on a *gross* basis before costs.
The 10 bps taker fee + 2–5 bps spread/slippage assumptions are not what is sinking ETH — the
underlying signal is genuinely negative-expectancy on this data.

**Sample size is not the story either.** Every (symbol, config) pair cleared the ≥20-trade
floor (BTC: 26–40 trades; ETH: 28–47 trades) — `LOW_TRADE_COUNT` never fires. The negative ETH
result is not an artifact of too few trades.

## 6. Fold robustness

For BTC, 14 of 15 configs have 2 of 3 OOS folds net-positive (the walk-forward robustness
criterion); only `conservative_regime` concentrates its (small) profit into a single fold and
is correctly flagged and correctly fails the gate on that basis, independent of the
BTC-vs-ETH question. No BTC config is a single-fold fluke that the gate incorrectly let through.

## 7. Conclusion

BTC/USDT passing 14/15 configurations while ETH/USDT passes 0/15 is not evidence of a flaky
gate or a data problem — it is a consistent, quantitatively explained result: this
configuration grid's edge is carried almost entirely by `trend_agent_v1`'s behavior on BTC
specifically, and that same behavior is a net loser on ETH. Any future evidence for ETH would
need either (a) a genuinely different strategy/config tuned for ETH's price dynamics rather
than a parameter variant of the BTC-tuned baseline, or (b) an asset-aware agent that does not
assume trend-following transfers uniformly across symbols — which motivates the exact
asset/timeframe evidence binding built in this checkpoint (`ASSET_SPECIFIC_EVIDENCE_POLICY.md`)
and the dynamic universe work for future symbols beyond BTC/ETH.
